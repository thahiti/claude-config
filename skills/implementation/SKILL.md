# Implementation

## Overview

문제를 푸는 가장 작은 코드를 쓴다. 판단이 갈릴 때는 지금 필요한 것과 나중에 필요할 것 같은 것을
구분하고, 나중 것은 쓰지 않는다.

이 스킬은 언어 공통 규칙만 담는다. Python 작업은 **stack-python** 스킬을 함께 본다.

## 최소 구현

- 요청받은 문제만 해결한다. 요청 범위를 넘는 기능을 얹지 않는다.
- 지금 호출자가 하나뿐인 코드에는 확장점을 만들지 않는다. 두 번째 호출자가 생겼을 때
  그때 추상화한다. 미리 만든 확장점은 대부분 실제 요구와 어긋나고, 어긋난 추상화는
  없느니만 못하다.
- 설정 항목, 플래그, 훅을 "혹시 몰라서" 추가하지 않는다. 늘어난 분기는 전부 테스트 대상이 된다.
- 이미 있는 코드로 해결되면 새로 쓰지 않는다. 새로 쓰기 전에 같은 일을 하는 함수가
  저장소에 있는지 먼저 찾는다.

## 스타일

- 함수형 스타일을 기본으로 한다. 입력을 받아 새 값을 돌려주는 순수 함수를 우선하고,
  상태 변경은 가장자리로 몰아낸다. 중간 단계에서 인자를 제자리 수정하지 않는다.
- SOLID 를 따른다. 특히 한 함수가 하는 일이 하나인지, 이름이 그 하나를 정확히 말하는지 본다.
- 주변 코드의 관습을 따른다. 네이밍, 주석 밀도, 에러 처리 방식을 그 파일에 맞춘다.
  개인 취향을 이유로 기존 스타일을 바꾸지 않는다.
- 타입을 명시한다. 타입 시스템이 있는 언어에서 추론에 기대 시그니처를 비워두지 않는다.
- trailing space 를 만들지 않는다.

## 진행 방식

- 불명확한 부분이 있으면 추측해서 채우지 말고 묻는다. 특히 요구사항의 경계,
  기존 동작을 바꿔도 되는지, 어느 계층에 넣어야 하는지가 갈릴 때는 묻는 편이 싸다.
- 지시받은 분량을 끝내면 멈추고 다음 단계를 확인한다. 흐름을 이어 다음 작업까지
  진행하지 않는다.
- 여러 해결 방법이 있으면 하나를 고르되, 버린 대안과 버린 이유를 한 줄로 남긴다.

## 에러 처리

- 삼키지 않는다. `catch` 로 잡아 로그만 남기고 넘어가면 호출자는 실패를 알 수 없다.
  복구할 수 없으면 올려보낸다.
- 실패 메시지에 판단에 필요한 값을 담는다. "failed to parse" 대신 어떤 입력의
  몇 번째 위치에서 무엇을 기대했는지 적는다.
- 방어 코드로 증상을 덮지 않는다. `if x is None: return` 을 넣기 전에 왜 None 이
  들어오는지를 먼저 확인한다. 근본 원인을 모른 채 넣은 가드는 버그를 나중으로 미룰 뿐이다.

## Common Mistakes

| 실수 | 왜 문제인가 |
|---|---|
| 호출자가 하나인데 인터페이스부터 정의 | 실제 두 번째 구현이 나오면 대개 맞지 않아 다시 뜯는다 |
| 요청에 없는 기능을 서비스로 추가 | 리뷰 범위가 넓어지고 유지보수 대상만 늘어난다 |
| 기존 스타일을 무시하고 새 관습 도입 | 한 저장소 안에 규칙이 둘이 되어 다음 사람이 어느 쪽을 따를지 모른다 |
| 원인 모른 채 None 가드 추가 | 증상만 사라지고 잘못된 값이 더 깊은 곳까지 흘러간다 |
| 불명확한 부분을 추측으로 채움 | 틀리면 그 위에 쌓은 작업까지 되돌려야 한다 |
