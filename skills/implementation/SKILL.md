# Implementation

## Overview

문제를 푸는 가장 작은 코드를 쓴다. 판단이 갈릴 때는 지금 필요한 것과 나중에 필요할 것 같은 것을
구분하고, 나중 것은 쓰지 않는다.

이 스킬은 언어 공통 규칙만 담는다. Python 작업은 **stack-python** 스킬을 함께 본다.

## 최소 구현 (YAGNI)

이 절의 항목은 권고가 아니라 구현 제약이다. "원칙" 으로 읽으면 소프트한 선호가 되고 결국 과하게 만든다.

- 요청받은 문제만 해결한다. 요청 범위를 넘는 기능을 얹지 않는다.
- 추상화는 구체적인 use case 가 **둘 이상** 일 때 도입한다. 하나뿐이면 그 자리에 직접 구현하고,
  두 번째가 나타나는 시점에 추출한다. factory, strategy enum, 범용 테이블, 플랫폼 계층처럼
  손이 먼저 가는 구조일수록 이 기준을 그대로 적용한다.
- 설정 키, 인터페이스 메서드, 기능 플래그, 워크플로 분기는 받아들여진 use case 없이 추가하지 않는다.
  이 넷은 원칙에는 동의하면서도 슬쩍 늘어나는 항목이라 이름을 적어둔다.
- 공통 유틸 추출은 같은 패턴이 **세 번** 나오고 모양이 굳은 뒤에 한다. 두 번째 중복에서 뽑아낸
  헬퍼는 세 번째 사례가 나오면 대개 맞지 않는다.
- 이미 있는 코드로 해결되면 새로 쓰지 않는다. 저장소, 표준 라이브러리, 이미 설치된 의존성
  순으로 먼저 찾는다.
- 지원하지 않는 경로는 조용한 no-op 이나 부분적인 흉내 구현 대신 명시적인 에러로 끝낸다.

개수 기준보다 앞서는 예외가 셋 있다. 검증된 재사용 사례가 있을 때, 외부에 공개하는 인터페이스
계약일 때, 팀이 명시적으로 결정했을 때다.

## 결과물의 형태

간결함은 금지 목록으로 조절되지 않는다. 결과물이 무엇인지를 먼저 정한다.

- 기본값은 이미 있는 것을 쓰는 것이다. 한 줄로 되는 일은 한 줄로 쓴다.
- 200줄을 썼는데 50줄로 될 것 같으면 다시 쓴다.
- 함수는 하나의 목적만 갖는다. 인자 하나로 로직이 갈리는 플래그 파라미터를 만들지 않는다.
  갈라야 하면 함수를 나눈다.
- 단발성 헬퍼를 미리 뽑지 않는다. 재사용되거나, 복잡한 경계를 감추거나, 독립적인 이름이
  호출부를 더 읽기 좋게 만드는 경우가 아니면 호출 지점에 그대로 둔다.

**깎지 않는 것.** 입력 검증, 에러 처리, 보안, 접근성, 그리고 사용자가 명시적으로 요청한 것은
간결함을 이유로 줄이지 않는다. 분량을 줄이라는 지시는 범위를 줄이라는 뜻이지 안전성을
줄이라는 뜻이 아니다.

## 주석

주석은 코드가 말하지 못하는 것만 적는다.

- 무엇을 하는지는 코드가 말한다. 주석에는 **왜** 그렇게 했는지를 적는다. 판단이 갈렸던 지점,
  겉보기와 다른 제약, 버린 대안이 대상이다.
- 코드를 그대로 옮긴 주석은 지운다. 코드가 바뀔 때 같이 바뀌지 않아 언젠가 거짓이 된다.
- 변경 사항을 설명하는 문장을 코드 안에 남기지 않는다. 그것은 커밋 메시지의 몫이다.
- 주변 코드의 주석 밀도를 따른다. 혼자만 촘촘하면 그 자체가 노이즈다.

## 스타일

- 함수형 스타일을 기본으로 한다. 입력을 받아 새 값을 돌려주는 순수 함수를 우선하고,
  상태 변경은 가장자리로 몰아낸다. 중간 단계에서 인자를 제자리 수정하지 않는다.
- SOLID 를 따른다. 그중 diff 에서 확인할 수 있는 형태로 옮기면 이렇다. 모듈과 패키지는
  하나의 관심사에 집중시키고, 새 동작은 기존의 좁은 인터페이스를 구현하는 방식으로 붙인다.
  기존 인터페이스에 관련 없는 메서드를 추가하지 않고 필요하면 새 인터페이스를 정의한다.
- 주변 코드의 관습을 따른다. 네이밍과 에러 처리 방식을 그 파일에 맞춘다. 개인 취향을 이유로
  기존 스타일을 바꾸지 않는다.
- 타입을 명시한다. 타입 시스템이 있는 언어에서 추론에 기대 시그니처를 비워두지 않는다.
- trailing space 를 만들지 않는다.

## 에러 처리

**기본 자세는 핸들러를 붙이지 않는 것이고, 붙이려면 이유를 댈 수 있어야 한다.** 성공하거나,
분명한 에러로 실패하거나 둘 중 하나로 만든다.

방어 코드는 몰라서 넣는 것이 아니라 맞춰주려는 성향 때문에 넣는다. 어떤 심리로 손이 가는지를
함께 적는 이유다.

| 하지 않는 것 | 손이 가는 이유 | 실제로 벌어지는 일 |
|---|---|---|
| 일어날 수 없는 상태에 가드 | 꼼꼼해 보인다 | 테스트할 수 없는 경로가 늘고, 진짜 실패 하나가 상상 속 실패 다섯 개에 묻힌다 |
| "혹시 몰라서" 넣는 fallback | 사용자에게 맞춰주는 동작으로 느껴진다 | 버그가 발생 지점이 아니라 세 계층 아래에서 드러난다 |
| 이미 검증을 통과한 값을 재검증 | 계층마다 방어하는 것이 안전해 보인다 | 같은 조건이 여러 곳에 복제되어 규칙을 바꿀 때 한 곳을 빠뜨린다 |
| 실패를 조용히 흡수하는 복구 | 흐름이 안 끊겨 깔끔해 보인다 | 호출자가 실패를 모른 채 잘못된 값으로 계속 진행한다 |
| catch-all 로 전부 포획 | 어떤 예외가 오는지 모를 때 편하다 | 근본 원인을 가린다. 무엇을 잡을지 확인해서 지정한다 |

판단 기준은 하나다. **이 값이 검증기를 통과했는가.** 검증기를 거치지 않고 들어오거나,
검증 이후 더 위험한 형태로 변환된 값에만 가드를 붙인다.

나머지는 이렇다.

- 실패 메시지에 판단에 필요한 값을 담는다. "failed to parse" 대신 어떤 입력의 몇 번째
  위치에서 무엇을 기대했는지 적는다.
- 재시도는 허용한다. 외부 API 호출처럼 일시적 실패가 실재하는 곳에서는 재시도하되,
  마지막에 마지막 에러를 그대로 올린다. 재시도가 실패를 삼키는 수단이 되면 안 된다.
- `if x is None: return` 을 넣기 전에 왜 None 이 들어오는지 확인한다. 근본 원인을 모른 채
  넣은 가드는 버그를 나중으로 미룰 뿐이다.

## 진행 방식

- 불명확한 부분이 있으면 추측해서 채우지 말고 묻는다. 요구사항의 경계, 기존 동작을 바꿔도
  되는지, 어느 계층에 넣어야 하는지가 갈릴 때는 묻는 편이 싸다.
- 지시받은 분량을 끝내면 멈추고 다음 단계를 확인한다. 흐름을 이어 다음 작업까지 진행하지 않는다.
- 여러 해결 방법이 있으면 하나를 고르되, 버린 대안과 버린 이유를 한 줄로 남긴다.

## Common Mistakes

| 실수 | 왜 문제인가 |
|---|---|
| 호출자가 하나인데 인터페이스부터 정의 | 실제 두 번째 구현이 나오면 대개 맞지 않아 다시 뜯는다 |
| 두 번째 중복에서 바로 공통 함수 추출 | 세 번째 사례가 나오면 모양이 달라 또 뜯는다 |
| 요청에 없는 설정 키나 플래그 추가 | 분기마다 테스트 대상이 늘고 아무도 쓰지 않는 경로가 남는다 |
| 일어날 수 없는 상태에 가드 추가 | 테스트할 수 없는 경로가 생기고 진짜 실패가 묻힌다 |
| 플래그 인자로 동작 모드를 분기 | 한 함수가 두 가지 일을 하게 되어 이름이 실제 동작을 말하지 못한다 |
| 미지원 경로를 조용한 no-op 으로 처리 | 호출자는 성공한 줄 알고 다음 단계로 넘어간다 |
| 원인 모른 채 None 가드 추가 | 증상만 사라지고 잘못된 값이 더 깊은 곳까지 흘러간다 |
| 코드를 그대로 옮긴 주석 | 코드가 바뀌어도 따라 바뀌지 않아 거짓이 된다 |
| 기존 스타일을 무시하고 새 관습 도입 | 한 저장소에 규칙이 둘이 되어 다음 사람이 어느 쪽을 따를지 모른다 |
| 불명확한 부분을 추측으로 채움 | 틀리면 그 위에 쌓은 작업까지 되돌려야 한다 |
