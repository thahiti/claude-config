# `/blog-draft` 스킬 설계

- 작성일: 2026-05-22
- 상태: 설계 승인 완료 (구현 계획 작성 전)

## 1. 배경과 문제

기존 `/blog-post` 스킬은 **발행 전용**이다. 로컬 md 파일을 GitHub API로 Jekyll 블로그에 업로드할 뿐, 본문 컨텐츠는 손대지 않는다(이미지 경로 치환만 예외). 즉 거친 초안을 블로그에 어울리는 글로 **다듬는 단계가 없다**.

`/blog-draft`는 그 빠진 단계를 채운다. 거친 초안을 받아, 기존 블로그 글들과 동질감 있고 논리적으로 탄탄한 완성본으로 다듬은 뒤 `/blog-post`에 넘긴다.

## 2. 목표 / 비목표

### 목표
- 거친 초안 md → 기존 블로그와 **동질감** 있고 **논리적으로 탄탄한** 완성 md
- **다중 출처 통합:** 여러 출처(다른 블로그 글, AI 대화 발췌, 기타 텍스트)를 한 파일에 모아 붙여 넣은 경우, 전체를 분석해 일관되고 논리적으로 구조화된 단일 포스트 초안으로 통합 (11장)
- `frontmatter`(태그·카테고리·내부 링크)까지 채워 `/blog-post`가 바로 발행할 수 있는 상태로 산출
- `git diff` 기반의 반복(iteration) 검토 흐름 제공

### 비목표 (스코프 경계)
- 다이어그램·이미지 **생성** 안 함 — "여기 시각자료가 있으면 좋겠다"는 *플래그*만 한다
- `/blog-post` 수정 안 함 — 기존 스킬 그대로 사용
- 외부 글쓰기 루브릭(예: AI 친화적 글쓰기 가이드)을 적용하지 않음 — 기준은 **블로그 코퍼스 자체에서 경험적으로 도출**한다

## 3. 역할 분담

| 스킬 | 역할 |
|------|------|
| `/blog-draft` | **지능** — 진단·재구성·교정·톤 일치·교차참조. frontmatter까지 채운 완성 md 산출 |
| `/blog-post` | **발행** — 완성된 md를 gh API로 업로드 (기존 그대로) |

흐름: `blog-draft` → (검토·반복) → `blog-post`.

## 4. 입력 / 출력 계약

- **입력:** `/blog-draft <rough-draft-md-path>` — 거친 초안 *또는* 여러 출처를 한 파일에 모아 붙여 넣은 콜라주 md 파일 경로 (repo 안/밖 무관)
- **출력:** worktree 안의 `_posts/YYYY-MM-DD-slug.md` — frontmatter가 완성된 최종 md
- **연결:** 발행 승인 시 이 경로를 그대로 `/blog-post`에 전달

## 5. 작업 공간

- 기존 repo(`thahiti.github.io`) 기반 **git worktree** + 스크래치 브랜치 `draft/<slug>` 사용
- superpowers `using-git-worktrees` 스킬 활용
- worktree 생성 전 `git pull`로 `main` 동기화 (톤 분석·교차참조가 최신 코퍼스를 보도록)
- 별도 fresh clone을 만들지 않는다 (사본 중복·정리 부담 회피)
- worktree/브랜치는 **버려지는 스크래치** — `/blog-post`가 최종 파일을 API로 발행하므로 `main`에 머지하지 않는다
  - 발행 완료 시: worktree·브랜치 정리(삭제)
  - 발행 거부 시: worktree 유지 + 재개 방법 안내

## 6. 워크플로 (10단계)

1. **사전 점검** — `gh` 인증, 현재 위치가 `thahiti.github.io` repo인지 확인
2. **워크스페이스 준비** — `git pull`로 `main` 동기화 → worktree + 스크래치 브랜치 `draft/<slug>` 생성
3. **원본 안착 + baseline 커밋** — 입력 파일(초안 또는 콜라주)을 worktree의 최종 경로(`_posts/YYYY-MM-DD-slug.md`)로 복사 → `draft: original` 커밋. 이 커밋 SHA를 **baseline 기준점**으로 기록
4. **스타일 프로파일 도출** — worktree의 기존 `_posts/*.md`를 전수 정독해 블로그의 톤·매너·구성 관습을 스타일 프로파일로 정리. 동시에 관련 주제·기존 태그/카테고리 체계 파악. 이 프로파일이 진단의 측정자(measuring stick)
5. **진단** — 먼저 입력이 단일 초안인지 다중 출처 콜라주인지 판별한다(11장). 단일 초안이면 5축 루브릭(7장)으로 분석해 진단 리포트(8장 형식)를, 콜라주면 통합 구조안(11장)을 생성한다
6. **계획 제시 + 승인** — 진단 리포트(또는 통합 구조안) = 변경 계획. 사용자 승인 (수정 요청 시 계획 조정)
7. **일괄 적용** — 승인된 계획을 적용하고(콜라주 입력의 첫 라운드는 통합 초안 작성, 이후 라운드는 구조 재배치·문장 교정·frontmatter 기입), **이번 라운드 전체를 하나의 커밋**으로 생성. 한 리뷰 라운드 = 한 커밋
8. **리뷰 안내** — 적용 직전에 기록해 둔 SHA를 사용해 명시적 diff 명령 안내:
   - 이번 라운드: `git diff --word-diff <라운드 직전 SHA> HEAD`
   - 누적 변경: `git diff --word-diff <baseline SHA> HEAD`
9. **Iteration** — 추가 수정 요청 시: 현재 라운드 직전 SHA 기록 → 적용 → 단일 커밋 → 8로 반복. 한 라운드 = 한 커밋이므로 각 라운드의 변경을 커밋 단위로 깔끔하게 되짚을 수 있다
10. **마무리** — 사용자 만족 시 "이대로 발행할까요?" 확인 → 승인 시 최종 md 경로로 `/blog-post` 호출 → worktree·브랜치 정리. 거부 시 worktree 유지

## 7. 진단 루브릭 (5개 축)

기준은 외부 규칙이 아니라 **블로그 코퍼스에서 경험적으로 도출**한다. 4단계의 스타일 프로파일이 A축의 측정자다.

**A. 톤·매너 동질감 (핵심 축)** — 스타일 프로파일 대비 평가
- 어미체·경어체
- 문장 길이·리듬·호흡
- 어휘 수준, 전문용어를 풀어 쓰는 방식
- 전개 방식 — 예시·비유 빈도, 도입부·마무리 패턴
- 헤딩·단락·코드블록·표 사용 *관습* (이 블로그가 실제로 하는 방식)
- → 핵심 질문: 초안이 **"같은 블로그의 글"로 읽히는가**

**B. 논리적 탄탄함 (핵심 축)** — 주장–근거 연결, 논리 비약·구멍, 도입→전개→결론 흐름, 내부 모순·용어 불일치

**C. 문장·표현 교정** — 어색한 표현·어미·문법 오류, 가독성

**D. 부족한 부분** — 빈약한 섹션·설명 누락

**E. 교차참조 → frontmatter** — 관련 기존 글 내부 링크, 기존 태그·카테고리 체계와 일치하는 제안

> A·B가 우선 축이다. **동질감과 논리**가 통과 기준이고, C/D/E는 이를 받친다.

## 8. 진단 리포트 형식

- **A축:** `스타일 프로파일 ↔ 초안` 대조표 (항목별 일치/이탈 표시)
- **B~E축:** 항목별 `위치 → 문제 → 제안`
- 이 리포트가 곧 6단계의 변경 계획이 된다

## 9. 부족한 부분(D) 처리 정책

CLAUDE.md "확실하지 않은 정보는 추측하지 말 것" 원칙에 따른다.

- 약한 부분을 진단 리포트에 표시하고 보강 *방향*을 제안한다
- 보강에 원문에 없는 **사실**이 필요하면 → 지어내지 않고 **사용자에게 질문**한다
- 본문 반영은 계획 승인 후에만 한다

## 10. 엣지 케이스

| 상황 | 대응 |
|------|------|
| 입력 md 없음 / repo 밖에서 실행 | 안내 후 종료 |
| `gh` 미인증 | `gh auth login` 안내 |
| `git pull` 충돌·실패 | 안내 후 사용자 결정 대기 |
| worktree 생성 실패 | 안내 후 종료 |
| 보강에 필요한 사실 부재 | 지어내지 않고 사용자에게 질문 |
| 발행 거부 | worktree 유지 + 재개 방법 안내 |
| 동일 날짜+slug 포스트 존재 | `/blog-post` 단계에서 덮어쓰기 확인 |

## 11. 통합 모드 — 다중 출처 입력

**적용 상황:** 입력 파일이 단일한 거친 초안이 아니라, 여러 출처(다른 블로그 글, AI 대화 발췌, 메모, 기타 텍스트)를 한 파일에 모아 붙여 넣은 "콜라주"일 때.

**감지:** 진단(워크플로 5단계)에서 입력을 분석해 다음 신호로 콜라주 여부를 판별한다.
- 한 파일 안에 이질적인 주제·문체·서술 시점이 혼재
- AI 대화 발췌의 흔적 (역할 레이블, 질의응답 형태 등)
- 출처별로 끊기는 맥락, 중복·상충하는 서술
- 명시적 구분선이나 붙여넣기 경계

콜라주로 판단되면 사용자에게 "다중 출처로 보입니다 — 통합 초안을 생성할까요?"로 확인한 뒤 진행한다.

**통합 구조안:** 콜라주로 확정되면 5단계 진단의 산출물이 일반 진단 리포트 대신 **통합 구조안**이 된다.
- 전체를 관통하는 핵심 주제·메시지 도출
- 도입→전개→결론의 일관되고 논리적인 목차(아웃라인) 제안
- 각 출처 조각을 어느 섹션에 배치할지 매핑
- 중복 내용 통합, 상충 내용 표시, 본문에서 뺄 조각 표시
- 출처 사이의 빈 논리 연결고리는 "부족한 부분"으로 플래그 (9장 정책 — 무단 사실 생성 금지, 필요 시 사용자에게 질문)

**워크플로 통합:** 통합 모드는 별도 단계를 추가하지 않고 기존 워크플로에 그대로 얹힌다.
- 3단계 baseline 커밋 = 원본 콜라주 그대로
- 6단계 = 통합 구조안 승인
- 7단계 = 승인된 구조로 통합 초안을 작성해 단일 커밋. `git diff <baseline> HEAD`가 "콜라주 → 정돈된 포스트" 변환 전체를 보여준다
- 8·9단계 = 이후 라운드에서 통상의 5축 교정으로 다듬기 반복

요컨대 **콜라주 입력은 "1라운드 = 통합, 2라운드 이후 = 정련"**, 단일 초안 입력은 "1라운드부터 정련"이다.

## 12. 추후 고려 (현재 비적용 — YAGNI)

- 스타일 프로파일 캐싱: 현재는 매 실행 시 코퍼스에서 새로 산출(항상 최신). 포스트가 많아지면 캐싱 검토
